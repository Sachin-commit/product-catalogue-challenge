# Decisions and assumptions

## Stack

| Layer | Choice | Why |
|---|---|---|
| Client | iOS in Swift with UIKit, programmatic (iOS 17+, Swift 6 strict concurrency) | Strongest stack of the person who has to defend and live-edit it. The brief allows it. The trade-off: reviewers need Xcode, while a React app would need only a browser. UIKit rather than SwiftUI: see "Deviations" below. |
| Backend | Node.js + TypeScript, Express 5 | The brief's preferred option. Express is boring, well understood and easy to explain. A heavier framework (NestJS) would add ceremony a PoC doesn't need. The ports/adapters split gives the same seams. |
| Validation | zod | One library for env config, HTTP input and upstream (Fake Store) responses. |
| Email | SMTP via nodemailer + Mailpit locally | Free, no account, runs in Docker. The reviewer sees the "sales inbox" at `localhost:8025`. The same adapter works with the AWS SES SMTP endpoint. |
| Tests | Vitest + supertest; Swift Testing | Fast, no network. |

## Assumptions (where the acceptance criteria were unclear)

1. **"Top rated" on the home page means the owner's curated choice**, not customer ratings. The criteria say
   "GIVEN *I have chosen* 5 products". Picks live in `backend/data/merchandising.json`, in display order.
   I chose #17 on purpose: it is not the best-rated women's item, which shows the curation is respected.
   If a picked product disappears from the data source, the home page tops up with the best customer-rated
   products and logs a warning instead of showing a gap.
2. **"Top rated for that category"** means: the owner's picks that belong to the category first, then the best
   customer-rated products, up to **3**. Without the rating fallback the strip would be empty for most
   categories, since only 5 products are curated across the whole catalogue. "Additional products" is
   everything else in the category, best-rated first.
3. **Search** runs on the backend, because Fake Store has no search endpoint and every client should get the same
   results. It is case- and accent-insensitive and looks at the title, description and category name.
   Every word in the term must match (AND), so adding words narrows the results.
   A word matches the **start of a word** in the product text, not any substring; otherwise "men" would return
   women's clothing. Results with matches in the title come first. Blank terms are rejected (400) and the app
   disables the button for them. Terms are capped at 100 characters.
4. **Search is triggered by an explicit Search button** (and the keyboard's Search key), as the criteria say
   "WHEN I click the search button". It does not search as you type.
5. **Enquiry form:** name and email are required; phone and message are optional. Product id comes from the page.
   The email goes to `SALES_INBOX` with `Reply-To` set to the customer, so sales can just hit reply.
6. **"Thank you" only after the email is accepted.** If the email provider fails, the customer sees a
   retryable error instead of a thank-you for an enquiry that was lost. The thank-you shows an enquiry
   reference (e.g. `ENQ-7F3A9C1B`) that also appears in the email subject.
7. **Prices are USD.** Fake Store has no currency; prices are stored as integer cents with a currency code
   and formatted on the device for the user's locale.
8. **Categories** come from the data: slugs are generated by the backend (`men's clothing` → `mens-clothing`).
   Fake Store's spelling "jewelery" is kept as-is because it is the source's data, not ours to rewrite.

## Requirements dropped or simplified, and why

- **Enquiries are not stored.** For the PoC the email is the record. Next step: persist enquiries (DynamoDB or
  Postgres) and send email from a queue, so an email outage delays enquiries instead of losing them.
- **No customer confirmation email.** Not in the criteria, and it doubles the abuse surface of an
  unauthenticated form.
- **No CAPTCHA.** Rate limiting (10 per 15 minutes per IP) is the only abuse protection. The limiter is in-memory,
  so it is per instance; scaling out needs a shared store (ElastiCache).
- **No pagination.** The catalogue has 20 products. The API returns full lists; a larger source needs cursor pagination.
- **Merchandising is a JSON file read at startup.** Changing picks needs a restart. A CMS or admin screen replaces it.
- **No offline cache in the app.** Fresh data on every launch; pull to refresh everywhere.
- **Accessibility is a basic pass:** Dynamic Type via text styles, VoiceOver labels on tiles, ratings and errors.
  No full audit.
- **No app icon, launch screen or brand.** The look and feel is still being designed; the `Theme` is a placeholder.

## Deviations from the agreed plan

- **Dropped XcodeGen.** Xcode 16's synchronized folders give the same benefit (new files need no project edits,
  so no merge conflicts in `project.pbxproj`) without an extra tool for reviewers to install.
- **Added a `fakestore-snapshot` product source.** The AI agent's sandbox could not reach fakestoreapi.com. A
  recorded copy also makes demos and CI independent of a third-party free service.
- **iOS client tests inject a transport closure instead of using `URLProtocol` stubs.** No global mutable
  state, so Swift Testing can run them in parallel safely.
- **UI rebuilt in UIKit instead of SwiftUI**, after the first version was working. SwiftUI already satisfied
  "iOS app in Swift", but I chose UIKit as the framework I'd most confidently change live in the follow-up.
  Screens are built in code (no storyboards), with a coordinator (`AppCoordinator`) owning navigation,
  compositional layouts with diffable data sources, and `UIContentUnavailableConfiguration` for loading, empty
  and error states. The view models, networking and models did not change: they are plain `@Observable` classes
  with no UI framework in them, and the screens follow them through a small `renderOnChange` helper built on
  `withObservationTracking`. Their tests passed untouched, which is the seam doing its job.
- **Product images are served by the backend** (see above), added after a gap review against the brief.
- **iOS restructured into Clean Architecture layers (Domain / Data / Presentation) with MVVM-C**, after an
  architecture review. This reverses an earlier call that the app's models could simply be the API's JSON shapes
  ("the backend is a BFF, so a mapping layer only duplicates it"). On review that coupled every screen to the
  wire format, let `APIError` leak into view models, and left business rules in views (search-term limits) and
  view models (enquiry validation). Now: domain entities with no `Codable`; DTOs and mapping in Data; one use
  case per user action; repository protocols owned by Domain; domain errors translated from transport errors;
  formatting and copy in Presentation; navigation decided by view models through small protocols; one
  composition root. The cost is more types for a small app, each of which has to earn its place; the thin
  pass-through use cases are the weakest case and are kept for consistency and as the home for future rules.
  The layers live in one module, so boundaries are enforced by `ios/scripts/check-architecture.sh` in CI rather
  than by the compiler; splitting them into Swift packages is the next step.

- **Images go through the backend too** (`GET /api/v1/products/:id/image`). The brief says the client must not
  call Fake Store; loading images from Fake Store's servers would have broken that rule and tied the app to the
  source's image URLs. The cost is an extra hop; responses are cacheable for a day. At scale, the API would
  redirect to a CDN (S3 + CloudFront) instead of streaming bytes.

## How the design supports growth beyond the PoC

```
iOS app ──HTTP──▶ Node API (/api/v1) ──▶ ProductRepository ──▶ Fake Store (API or snapshot)
                                     ├─▶ MerchandisingSource ─▶ merchandising.json
                                     └─▶ EmailSender ─────────▶ SMTP (Mailpit / SES)
```

- **Product data source will change.** The app talks only to our API; the API talks to a `ProductRepository`
  interface. Fake Store shapes never leave `adapters/fakestore`. Search and category filtering are part of the
  repository contract, so a database or search engine (OpenSearch, Algolia) can do them natively. A new source
  means one new adapter plus one line in `container.ts`, with no changes to services, routes or the app.
- **Email provider will change.** `EmailSender` is provider-neutral. Moving to SES is configuration (SES SMTP
  credentials); moving to the SES API or SendGrid is one new adapter.
- **Look and feel will change.** Every colour, font, spacing and radius comes from `Theme`. Re-skinning means
  setting a different `Theme.current` at launch; screens don't change. Xcode previews (`#Preview`) with sample
  data let designers iterate on screens without the backend's data.
- **The UI framework itself can change.** Moving from SwiftUI to UIKit replaced only the view layer; view
  models, networking and their tests were untouched.
- **The client's data source can change too.** The iOS Domain owns `CatalogueRepository`; adding an offline
  cache or a GraphQL client is a new Data-layer type plus one line in `AppContainer`.
- **The API is a versioned contract (`/api/v1`)** mapped from the domain in `presenters.ts`. Mobile apps
  can't be force-updated, so the domain can evolve while v1 stays stable.
- **A web client can be added** against the same API (it is a backend-for-frontend; a web BFF or CORS config
  would be added then).
- **AWS-ready:** stateless container with a health check, config from env vars, non-root image, `TRUST_PROXY`
  for running behind an ALB. ECS Fargate + ALB, Secrets Manager for SMTP credentials and SES for email would be
  the first deployment.
- **Resilience:** catalogue cached for 5 minutes with single-flight loading; if Fake Store goes down, stale data
  is served rather than errors, and upstream errors become a clean 502 with a customer-safe message.
